## 2. Компоненты и зоны ответственности

### 2.1. `telemetry.py` — канонический реестр переменных

Единственный источник правды о величинах: имя ключа, тип, единица, привязка к
SimVar (`sim_var`/`sim_unit`) и событие записи (`sim_event`). Профили ссылаются
только на эти ключи, поэтому переименование SimVar — правка в одном месте.

```python
Variable("power.batteryMaster", "bool", "Master battery",
         sim_var="ELECTRICAL MASTER BATTERY", sim_unit="bool",
         sim_event="TOGGLE_MASTER_BATTERY")
```

### 2.2. `sim/` — источники телеметрии (провайдеры)

Общий интерфейс `SimProvider`:

| Метод | Назначение |
| --- | --- |
| `connected` | живая ли связь с симулятором |
| `start()` / `stop()` | фоновый поток провайдера |
| `read()` | снимок значений `dict[key, value]` |
| `apply_command(key, value)` | применить команду клиента |
| `select_aircraft(profile_id)` | сменить борт (поддерживает только mock) |

Реализации:

- **`MockSim`** — процедурный полёт: банк/тангаж/курс/скорость/высота меняются
  по плавным синусоидам, топливо расходуется. Нужен для разработки без MSFS,
  демонстраций и автотестов.
- **`SimConnectSim`** — нативный SimConnect через `ctypes`. Подписывается на
  блок числовых датумов (`AddToDataDefinition` + `RequestDataOnSimObject`),
  отдельно на строковые `TITLE`/`ATC MODEL`, кэширует значения в `read()`,
  команды отправляет событиями (`MapClientEventToSimEvent` +
  `TransmitClientEvent`). Если пользовательский `SimConnect.cfg` указывает на
  несуществующий канал, подключение повторяется по TCP `127.0.0.1:19999`
  через временный конфиг (порт MSFS 2020/2024). Подключение к живому MSFS 2020
  проверено; живой полёт и WASM-модуль — следующий шаг валидации.

Фабрика `create_sim()` выбирает провайдера по настройке `--sim`:

- `mock` → всегда mock;
- `simconnect` → только SimConnect, при ошибке — завершение;
- `auto` → SimConnect, при неудаче откат на mock (шлюз всегда запускается).

### 2.3. `hub.py` — шина телеметрии

- один поток-«тикер» с частотой `--telemetry-hz` собирает `sim.read()` и
  рассылает кадр всем WebSocket-клиентам;
- у каждого клиента своя очередь (8 кадров) и поток-отправитель: медленный
  планшет не останавливает рассылку остальным, старые кадры выбрасываются;
- **rate-limit команд** (≤30/с на клиента) — защита от залипания касания;
- `build_message()` нормализует значения (round до 3 знаков, полный набор
  ключей), добавляет `seq`, `ts`, метаданные `sim`.

### 2.4. `profiles.py` + `legacy.py` — профили самолётов

- `validate_profile()` — строгая проверка структуры (типы приборов, привязки,
  команды, прямоугольники, диапазоны шкал);
- `ProfileStore` — потокобезопасное атомарное сохранение (tmp + `fsync` +
  `os.replace`);
- `legacy.adapt()` — преобразует «пиксельный» формат v0 из ТЗ во внутренний
  (координаты в долях 0..1), чтобы старые панели загружались как есть.

### 2.5. `http_api.py` + `websocket.py` — сеть

- `ThreadingHTTPServer` раздаёт статику `web/`, REST API и делает WebSocket
  upgrade на одном порту — одно правило брандмауэра;
- `websocket.py` — минимальный RFC 6455 (текст, ping/pong, close) на stdlib;
- `auth.py` — необязательный вход по паролю: PBKDF2-хеш, сессии в памяти,
  cookie `HttpOnly`, Bearer-токены, одноразовые QR-токены, лимит попыток;
- заголовки безопасности: CSP `default-src 'self'`, `X-Content-Type-Options`,
  `Referrer-Policy`; статика без кэша (живая разработка);
- `/api/connect` + `qr.py` — быстрое подключение телефона: хост перечисляет
  свои сетевые адреса (сначала `192.168.x`, затем `10.x`, `172.16-31.x`), а
  QR-код рисует собственный генератор на stdlib (байтовый режим, EC L,
  версии 1–10, все маски), без внешних библиотек и интернета.

### 2.5a. `auth.py` — вход по паролю

- Пароль хранится только как PBKDF2-хеш (`config/auth.json`), проверка —
  `hmac.compare_digest`, 5 неудач в минуту с адреса → блокировка.
- Сессии — в памяти процесса (32 байта, TTL 12 часов, продление по
  активности); браузер получает cookie `rud_session` (`HttpOnly`,
  `SameSite=Lax`), нативные клиенты — Bearer или `?token=` для WebSocket.
- Одноразовые QR-токены (`POST /api/pair`, 10 минут) позволяют телефону
  войти без ввода пароля.
- Публично доступны только вход, `/api/health`, `/api/integrity`,
  `/api/donation` и `/license`; остальное закрыто.

### 2.5b. `assist.py` — ассистенты посадки и руления

- **Руление**: ПИ-регулятор тяги по путевой скорости и П-регулятор руля по
  курсу; включается только на земле, выключается при отрыве/тормозе/скорости
  выше 35 уз; «СТОП» даёт тягу 0 и стояночный тормоз.
- **Посадка**: ARM включает AP и APR, на 60–15 футах линейно убирает тягу,
  на касании выключает AP; TOGA — полная тяга. Рули высоты не трогает.
- Поток 10 Гц читает `sim.read()` и отправляет команды через
  `Hub.apply_assist_command` (без rate-limit и лишнего чтения).
- Это вспомогательный контур: окончательное решение и контроль — за пилотом.

### 2.6. `integrity.py` — защита доната (условие лицензии)

Сверяет SHA-256 пяти критичных файлов (включая `web/js/ui/donation.js`,
`web/css/donation.css`, `config/donation.json`) с манифестом
`integrity/manifest.json`. Хост блокирует запуск при расхождении; клиент
(`web/js/ui/integrity.js`) дополнительно следит за видимостью блока в DOM.

### 2.7. `discovery.py` — автообнаружение хоста (UDP broadcast)

Фоновый поток рассылает JSON-бикон (имя хоста, версия, `httpPort`, частота,
список профилей) по UDP broadcast (`255.255.255.255` + направленный broadcast
каждого интерфейса) каждые N секунд. `listen_once()` — приёмник для нативных
клиентов и тестов. Браузер UDP не умеет, поэтому веб-клиент в этом не нуждается
(он и так запускается с самого хоста).

### 2.8. `web/editor.*` — визуальный редактор панелей

`/editor.html` + `web/js/editor.js` — drag-and-drop редактор: перетаскивание и
изменение размеров приборов, настройка привязок (выпадающие списки из каталога
`GET /api/telemetry/variables` плюс объявленные в профиле `custom.*`), опций
(шкалы, единицы, тона), добавление из палитры типов и удаление. Сохранение —
`PUT /api/profiles/{id}`. Предпросмотр рисует настоящие приборы (через реестр
`widgets/registry.js`) с демо-значениями. Переопределения под форм-фактор
правятся в активном форм-факторе: если переопределения нет — правка идёт в
`layout.base`. История правок (снимки `widgets` до изменения) даёт отмену и
повтор для перетаскивания, размеров, свойств, добавления и удаления; есть
привязка к сетке 1 % (Shift — временно выключить) и копирование геометрии в
другие форм-факторы одной кнопкой.

### 2.8a. Автоопределение борта

`SimConnectSim` читает `TITLE` и `ATC MODEL` отдельными строковыми датумами
(`SIMCONNECT_DATATYPE_STRING256`) и складывает их в `aircraft.title` /
`aircraft.atcModel`. `hub.py` держит правила `sim.match.title` / `atcModel`
(glob, регистронезависимо) и на каждом кадре выбирает профиль, если провайдер
не задаёт его сам. Клиент следит за `sim.profileId` в телеметрии и
перезагружает панель при смене борта; ручной выбор из списка закрепляется на
5 секунд, чтобы не спорить с ещё не доехавшим кадром.

### 2.8b. `web/js/ui/comfort.js` — яркость и киоск

Яркость панели — три ступени (100/72/45 %), хранится в `localStorage` и
применяется атрибутом `data-brightness` на `<html>`: CSS гасит только сцену
с приборами, интерфейс остаётся читаемым. Режим киоска скрывает верхнюю панель
и статус-бар, переводит сцену в full-режим и оставляет маленькую кнопку
выхода; `Esc` возвращает интерфейс. Шорткаты: `B` — яркость, `F` и `Esc` —
киоск.

### 2.9. WASM-мост: LVAR/RPN через Client Data Area

Сложные ВС (PMDG, Fenix, FlyByWire, iniBuilds) держат состояние в собственных
переменных. Профиль объявляет их блоком `variables` (`source: lvar` или
`rpn`), а мост читает/пишет их через **SimConnect Client Data Area** —
туда публикует данные WASM-модуль (MobiFlight / SimBridge).

```
hub.build_message()
   └─ hub._custom_values(profile_id)        # кэш 0.25 с
        └─ WasmBridge.read_specs(specs)      # wasm_bridge.py
             ├─ read_lvars(names)            # блок: имя 128 B + double 8 B
             └─ execute_rpn(script)          # Command → Response
                  └─ ClientDataChannel.read_area / write_area   # client_data.py
                       └─ SimConnectClientDataBackend            # simconnect.py
                            └─ run_on_dispatch(...)  # вызовы в потоке SimConnect
```

Слои:

- **`sim/client_data.py`** — протокол в синхронном виде: корреляция запросов по
  `request_id`, таймауты, повторная регистрация области при росте размера,
  сброс ожиданий при разрыве. Транспорт абстрагирован (`ClientDataBackend`),
  поэтому протокол тестируется без MSFS; `LoopbackClientDataBackend` —
  in-memory реализация для тестов и демо.
- **`sim/simconnect.py`** — `SimConnectClientDataBackend`: `MapClientDataNameToID`,
  `AddToClientDataDefinition`, `RequestClientData`, `SetClientData`. Все вызовы
  выполняются в потоке диспетчеризации через `run_on_dispatch` (SimConnect не
  рассчитан на многопоточные вызовы), ответы приходят в
  `SIMCONNECT_RECV_ID_CLIENT_DATA`.
- **`sim/wasm_bridge.py`** — раскладка блока LVAR, команды RPN, запись LVAR
  через `(<значение>) (>L:NAME, number)`.

Области по умолчанию: `MobiFlight.LVars`, `MobiFlight.Command`,
`MobiFlight.Response`; при другой версии модуля они переопределяются константами
в `wasm_bridge.py`.

Включается автоматически для провайдера `simconnect` (флаг `--no-wasm`
отключает). Если WASM-модуль не установлен, ответы не приходят, и через таймаут
ключи `custom.*` просто отсутствуют в кадре — приборы честно показывают «--»,
телеметрия SimVar продолжает работать. В mock-режиме значения берутся из
`initial` профиля.

**Статус проверки:** протокол и учёт областей покрыты тестами (эмуляция
MobiFlight через in-memory транспорт), сборка и запуск проверены; живой полёт
с MSFS + WASM-модулем ещё не прогонялся — это единственный шаг, который
требует установленного симулятора.

### 2.10. `android_build.py` — сборка Android APK из дистрибутива

В установленном приложении лежат исходники Android (`android/`) и готовый APK
(`android/dist`). Страница `/android.html` и API `/api/android/*` позволяют
поменять имя приложения, package id, версию и адрес шлюза по умолчанию,
запустить `gradle assembleDebug` и скачать свежий APK. Настройки —
`config/android-build.json`; те же значения передаются в сборку как `-P…`
и попадают в `BuildConfig`/манифест Android.

Поиск инструментов: настройки → `JAVA_HOME` / `ANDROID_HOME` → типовые пути.
Если профиль пользователя недоступен для записи (жёсткие политики, песочницы),
кэш Gradle, `TMP` и debug-keystore автоматически уводятся в каталог
дистрибутива (`.gradle-home`, `.tmp`, `.android-home`) — сборка продолжает
работать. CLI без браузера: `RudPanelGateway.exe --build-apk [config.json]`.

## 3. Поток данных

### 3.1. Телеметрия (push)

```
MockSim/SimConnectSim._loop()
   └─ sim.read()                        # снимок значений
        └─ hub.build_message()          # нормализация + seq/ts/sim
             └─ hub._broadcast_text()   # JSON в очередь каждого WebSocket
                  └─ web: handleMessage('telemetry') → store → panel-view → виджеты
```

### 3.2. Команда (request/ack)

```
web: toggle-switch.onClick()
   └─ socket.command(key, value)        # {type:'command', id, key, value}
        └─ hub.handle_command()         # валидация + rate-limit
             └─ sim.apply_command()     # mock / SimConnect
                  └─ ack {type:'ack', id, ok, value}   (по WebSocket)
                       └─ клиент ждёт подтверждения телеметрией
```

### 3.3. Профиль (pull)

```
web: api.listProfiles() → GET /api/profiles
   └─ api.getProfile(id) → GET /api/profiles/{id}
        └─ profiles.load_profile_file() → legacy.adapt_if_needed() → ensure_valid()
             └─ panel-view.mount(profile) → createWidgetInstance() по type
```

### 3.4. Автообнаружение (UDP push)

```
DiscoveryBeacon._loop()                      # поток-демон
   └─ payload() {name, version, httpPort, profiles, auth?, ts}
        └─ sendto(255.255.255.255:8761) + направленные broadcast
             └─ Android/нативный клиент: listen_once() → http://<ip>:<port>/
```

## 4. Ключевые проектные решения

| Решение | Почему |
| --- | --- |
| Python только stdlib | air-gapped: `pip install` недоступен; один интерпретатор уже установлен |
| Один порт для HTTP+WS | одно правило брандмауэра, проще диагностика |
| WebSocket без внешней библиотеки | контроль над протоколом, отсутствие зависимостей |
| Профиль — координаты 0..1, не пиксели | один профиль на всех форм-факторах |
| `layout.base` + переопределения | телефон/планшет задают только отличия |
| Канонический реестр SimVar | отделение профилей от конкретного моста |
| Сглаживание на клиенте (Smoother) | 60 fps анимация при 20–30 Гц сети |
| Виджет рисует canvas по `clientWidth` | честное HiDPI-масштабирование в превью |
| Провайдер `auto` | шлюз запускается без MSFS без правки конфигурации |
| UDP-бикон автообнаружения | Android находит хост без ручного IP; браузеру не нужен |

## 5. Границы MVP и следующие шаги

Что **уже есть**: шлюз на stdlib, WebSocket с очередями на клиента,
mock/SimConnect (+ TCP-фолбэк), WASM-мост LVAR/RPN, 9 типов приборов,
3 форм-фактора, профили с валидацией и атомарным сохранением, редактор с
undo/redo и копированием раскладки, UDP-автообнаружение, Android-клиент,
сборщик APK в дистрибутиве, установщик Windows, вход по паролю с QR,
ассистент посадки и руления, проверка целостности, 225 Python- и 29 JS-тестов.

Следующие шаги (см. README «Дорожная карта»):

- живая валидация полёта: SimConnect/WASM на реальном борту, ассистент в
  воздухе и на земле;
- release-подпись APK (keystore в настройках сборщика);
- mDNS (Bonjour) как альтернатива UDP-бикону;
- маршрутное руление по схемам аэропорта (сейчас ассистент держит только
  скорость и курс);
- запись/повтор телеметрии для демонстраций и профилирования.
